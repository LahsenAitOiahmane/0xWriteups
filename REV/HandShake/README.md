## Final Flag

NSC{wh0_kn0ck5_tw1c3_0wn5_th3_h4unt}

## Executive Summary

The binary implements a two-stage IPC handshake using Windows primitives:
- a named event
- a named shared memory mapping
- a hidden window that handles WM_COPYDATA and WM_TIMER

If the sequence is wrong (especially signaling too early), the program takes a punishment path and blocks the normal success flow. The intended path is:
1. Deliver a valid first signal through WM_COPYDATA.
2. Then trigger the second signal (named event).
3. Let the timer handler validate both state channels and derive the final flag.

A decoy NSC string is present in static data, but the real intended flag is generated by two chained PRNG/XOR transforms.

## High-Level Architecture

The binary behaves like a broker process with internal state gates.

### Core components
- Named event: Local\\TaskCache.SecondSignal
- Named mapping/object flow around TaskCache.DispatchNote
- Hidden class/window pair:
  - class: TaskCacheNotificationWindow
  - window: BackgroundTransferHost
- Periodic timer: id 0xBEEF

### Why this matters
The challenge is not just recovering constants. The logic enforces ordering across two channels (message + event). If order/state mismatches occur, failure flags are latched and the success branch is denied.

## Control-Flow Analysis

## 1) Startup / Seeding

`main_broker` computes a rolling diagnostic seed and prints status text similar to:
- Initialization failed.
- broker awaiting second signal.
- diagnostic seed: %08X

The process then initializes broker resources and enters a standard Windows message loop.

## 2) First Signal (WM_COPYDATA path)

In `broker_window_proc`, message 0x4A dispatches to `handle_first_signal_copydata`.

Key checks in this path:
- COPYDATASTRUCT exists and has data.
- dwData equals 0x5349474E (ASCII SIGN in little-endian form).
- Internal failure/early-signal flags are clear.
- Payload format is validated against runtime text formatting logic (SECOND:%08X:%08X path).

On success it arms internal state:
- writes ticket-like value (0x8C6EB98A) into mapped structure field
- writes KNOCK_OK marker into shared structure
- sets state required by timer-stage checks

## 3) Second Signal + Enforcement (WM_TIMER path)

`WM_TIMER` executes only for id 0xBEEF.

The timer path performs strict gating:
- waits/queries second signal object state
- validates shared-memory/property state
- validates transformed value equations:
  - value ^ 0xC001CAFE == 0x4C6F7374
  - multiple globals must match expected derived state

If checks fail, it marks error flags and can trigger the punishment branch (EARLY_SIGNAL behavior).

If checks pass, it calls `derive_second_stage_string` and reaches the success message path.

## "Punished" Logic Explained

The challenge hint is literal. Sequence/order matters.

Wrong order example:
- signaling event first (before a valid WM_COPYDATA first signal) latches failure and breaks the success path.

Intended order:
1. Valid first signal through COPYDATA.
2. Then second signal through event.
3. Timer validates both and unlocks final derivation.

## Deobfuscation Internals

## A) Decoy Blob (easy path, not final)

A static blob at 0x140023730 is XOR-decoded with 0x5A in `decode_startup_blob`.
This yields:

NSC{c0pyd4t4_b3f0r3_53t3v3nt}

This is a hint/instruction, not the intended final flag.

## B) Stage-1 Alphabet Builder (`build_lookup_alphabet`)

Input seed is transformed, then used in a 0x31-byte loop:

- seed = (seed ^ 0xD00DCAFE)
- each round:
  - seed = seed * 0x41C64E6D + 0x3039
  - output byte = ((i*7 + 0x33) ^ tbl1[i] ^ (seed >> 24)) & 0xFF

This builds an intermediate 49-byte alphabet-like buffer.

## C) Stage-2 Selector (`derive_second_stage_string`)

Second loop (0x24 bytes) indexes stage-1 output:

- s2 = (seed ^ 0xA55AA55A)
- each round:
  - s2 = s2 * 0x19660D + 0x3C6EF35F
  - idx = ((i*0x0D + 0x5D) ^ tbl2[i] ^ (s2 >> 24)) & 0xFF
  - out2[i] = out1[idx]

When the handshake seed state is correct (0x4C6F7374), stage-2 output is the final flag.

## Reproduction Script (Offline Derivation)

The following script reproduces the generator logic directly from binary bytes:

from pathlib import Path

exe = Path("H4ND5H4K3.exe").read_bytes()

# PE section mapping for this binary
rdata_vma = 0x14001B000
rdata_off = 0x19C00

def va_bytes(va, n):
    off = va - rdata_vma + rdata_off
    return exe[off:off+n]

tbl1 = va_bytes(0x140023858, 0x31)
tbl2 = va_bytes(0x140023890, 0x24)
seed = 0x4C6F7374

# stage 1
s1 = (seed ^ 0xD00DCAFE) & 0xFFFFFFFF
out1 = bytearray()
for i in range(0x31):
    s1 = (s1 * 0x41C64E6D + 0x3039) & 0xFFFFFFFF
    b = (((i * 7 + 0x33) & 0xFF) ^ tbl1[i] ^ ((s1 >> 24) & 0xFF)) & 0xFF
    out1.append(b)

# stage 2
s2 = (seed ^ 0xA55AA55A) & 0xFFFFFFFF
out2 = bytearray()
for i in range(0x24):
    s2 = (s2 * 0x19660D + 0x3C6EF35F) & 0xFFFFFFFF
    idx = (((i * 0x0D + 0x5D) & 0xFF) ^ tbl2[i] ^ ((s2 >> 24) & 0xFF)) & 0xFF
    out2.append(out1[idx])

print(out2.decode())
